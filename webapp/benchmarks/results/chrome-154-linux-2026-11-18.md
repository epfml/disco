The successful run recorded 195 cases: 65 configurations × three repetitions.

Machine: Intel Core i7-12800HX, 24 logical CPUs, 15.3 GiB RAM,
Linux 7.2.15-arch1-1 x64. Browser: headless Chrome for Testing 154.0.8037.57,

The run used the production peer implementation and adapter without modifications.

## Bridge-only round trips

The page-local echo excludes WebRTC and model serialization. Each round trip
crosses the worker boundary twice. Values below are medians pooled across the
three repetitions. Copy/transfer performs one explicit owned-buffer copy in each
direction, matching the production adapter's copying policy.

| Payload | Transfer-only control | Copy/transfer control | Production bridge |
| ------- | --------------------: | --------------------: | ----------------: |
| 1 KiB   |               0.10 ms |               0.10 ms |           0.10 ms |
| 64 KiB  |               0.10 ms |               0.30 ms |           0.20 ms |
| 1 MiB   |               0.10 ms |               2.10 ms |           1.30 ms |
| 16 MiB  |               0.00 ms |              14.45 ms |          14.15 ms |
| 64 MiB  |               0.10 ms |              55.45 ms |          56.75 ms |

**Inference:** copying/allocation dominates the bridge at large payload sizes.
The 64 MiB copy/transfer control and production adapter take about 55–57 ms,
while the transfer-only diagnostic remains near the clock resolution.
Transfer-only detaches/recycles the caller's buffer, so these measurements do not
justify swapping it into the existing caller-retains-ownership API unchanged.
Near-zero timings and extremely large _logical_ transfer throughputs represent
moving ownership, not memory bandwidth. The 1 MiB adapter/control ordering varies
with repetition and should not be read as a precise estimate of wrapper overhead.

## Real WebRTC loopback, one peer

These timings include the complete outbound WebRTC message and its echoed
response, including production fragmentation, flow control, reassembly and ACKs.
Both peers are in the same browser; STUN discovery uses the production configuration.

| Payload | Direct RTT | Worker-bridge RTT | Difference | Relative difference |
| ------- | ---------: | ----------------: | ---------: | ------------------: |
| 1 KiB   |    0.20 ms |           0.40 ms |   +0.20 ms |             +100.0% |
| 64 KiB  |    1.90 ms |           2.10 ms |   +0.20 ms |              +10.5% |
| 1 MiB   |   21.85 ms |          23.10 ms |   +1.25 ms |               +5.7% |

At 1–64 MiB, the observed one-peer median increase is roughly 3–6%.
This comparison measures the whole path, including scheduling and GC; the
subtracted medians are not a pure copy-cost measurement or a confidence interval.
Small-message percentages are especially sensitive to clock resolution.

| 64 KiB           |    5.90 ms |           6.10 ms |   +0.20 ms |
| 1 MiB            |   81.25 ms |          82.25 ms |   +1.00 ms |
| 16 MiB           | 1395.85 ms |        1408.85 ms |  +13.00 ms |

For 16 MiB × four peers, median aggregate bidirectional throughput is
88.2 MiB/s direct versus 86.5 MiB/s bridged. Differences are small relative to
between-repetition variation: the bridged per-repetition median RTT can be
slightly faster or slower. More repetitions would be needed to resolve that
small difference reliably. There is one outstanding message per peer; this is
not an unlimited-queue saturation test.

## Small CPU training-and-exchange workload

Each round trains one epoch of the production Titanic TFJS model on 128 fixed
synthetic samples, sends a 46,549-byte weight update through real WebRTC, and
decodes/reapplies the echoed weights. Both paths start from identical serialized
weights and use the CPU backend; this is not a full Disco distributed session.

| Metric                                 | Direct on page | Training in worker, bridged WebRTC |
| -------------------------------------- | -------------: | ---------------------------------: |
| Median total time per round            |       33.66 ms |                           35.72 ms |
| Median exchange RTT                    |        2.70 ms |                            2.70 ms |
| Median of case maximum page-timer lags |       36.10 ms |                            1.10 ms |

Total per-round timing overlaps across repetitions (direct: 33.0–35.0 ms;
bridged: 32.7–37.6 ms). It would be misleading to attribute the total median
difference entirely to transport: training execution also moved threads.
The page timer shows a clear responsiveness benefit in this small CPU workload.
Its observation window includes initialization and cleanup as well as training.

## Remaining page stalls and limits

At 64 MiB, bridged WebRTC still produces a median maximum page-timer lag of
58.2 ms, versus 35.1 ms direct. The bridged cases contain 54–59 ms Long Tasks.
Moving training off the page does not remove the page-side copying, chunking,
and reassembly costs for very large model updates.

These results support measuring an ownership-aware transfer path as a follow-up,
while retaining the worker design's responsiveness benefit. They do not establish
performance for large GPU training, a remote network, different browsers, or
many remote participants. Peak memory/native allocations were not measured.
The largest one-peer RTT estimates pool only 18 measured samples.
